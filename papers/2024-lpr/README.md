# LPR: Large Language Models-Aided Program Reduction

Paper: Mengxiao Zhang, Yongqiang Tian, Zhenyang Xu, Yiwen Dong, Shin Hwei Tan, Chengnian Sun, ISSTA 2024. DOI: `10.1145/3650212.3652126`.

Official artifact: https://github.com/zhangxiaosa/LPR (also archived on Zenodo, record 10901714).

## Core insight

LPR alternates a language-generic syntax reducer with language-specific transformations proposed by an LLM. The generic reducer first reaches a local 1-tree-minimal form; an LLM then performs semantics-aware rewrites that can expose new syntactic reduction opportunities, after which the generic reducer runs again.

The paper evaluates 50 compiler-bug benchmarks: 20 C, 20 Rust, and 10 JavaScript. It reports that LPR produces programs 24.93%, 4.47%, and 11.71% smaller than Vulcan for C, Rust, and JavaScript respectively, while also reducing user-perceived time on the evaluated suites.

## Reproduction level

**Current level: L1 partial.**

This directory reprocesses the authors' released reduced programs with the authors' own `token_counter_deploy.jar` and compares five LPR outputs per benchmark against the released Vulcan output. It does **not** rerun GPT-3.5/CodeLlama or the full reduction loop, so it is not L2 or L3.

The distinction matters because the artifact README explicitly says that LLM outputs are nondeterministic and that some precomputed results are reruns because the original RQ3 results were misplaced. Therefore matching released artifact outputs is evidence for the published claims, not a fresh end-to-end reproduction.

## Run

Requirements: Linux/macOS, Git, Python 3, and Java.

```bash
bash papers/2024-lpr/reproduce.sh
```

The script pins the official artifact to commit `d45ea0e261a8f4c7ec05fc29ccb5aadd19d673cc`, counts tokens in the released `vulcan` and `lpr_0..4` outputs, checks that all 50 benchmark cases are present, and writes:

- `results/results.json` — per-case and aggregate data;
- `results/summary.md` — compact paper-vs-artifact comparison.

GitHub Actions runs the same deterministic lane and uploads these files as an artifact.

## Experiment design

### L1 question

Do the author-released reduced programs support the headline effectiveness claim relative to Vulcan when token counts are independently recomputed using the artifact's own token counter?

For each language and benchmark case:

1. count tokens in `benchmark_suites/<lang>/vulcan/<case>/small.*`;
2. count tokens in each of `lpr_0` through `lpr_4`;
3. average the five LPR token counts for that case;
4. report both mean per-case improvement and ratio-of-total-token improvement;
5. compare the former with the paper's 24.93% / 4.47% / 11.71% headline values.

Using both aggregation formulas is deliberate: it makes the statistical aggregation convention visible rather than silently selecting the one closest to the paper.

| Item | Paper | This reproduction |

| Corpus | 20 C + 20 Rust + 10 JS | Same released 50-case corpus |
| LPR samples | LLM-dependent repeated experiments | Five released LPR outputs per case |
| Vulcan baseline | Vulcan | Released Vulcan output, recounted |
| Size metric | tokens | Authors' token-counter JAR |
| Fresh LLM calls | yes in paper | no |
| Reproduction level | paper-scale evaluation | **L1 partial** |

The exact numeric reprocessing result is generated by CI in `results/summary.md`; it is not hard-coded here so artifact drift cannot be hidden by documentation.

## Why no L2 today

The official instructions require either a paid OpenAI API key for `gpt-3.5-turbo-0125` or a locally served CodeLlama model. The documented Docker image is nearly 80 GB, and the README estimates roughly 40 hours for a full single-thread C LPR run. A fresh L2 therefore requires a model endpoint/API secret plus a controlled compiler/reducer environment. This deterministic lane intentionally does not consume user secrets or claim a live reproduction.

### Upgrade path to L2/L3

- **L2:** run one released compiler-bug case end-to-end using a pinned available LLM, Perses/Vulcan versions, prompt, temperature, seed where supported, and preserve the complete trajectory and oracle log.
- **L3:** run all 50 cases with repeated trials and the paper's budget, then report distributions rather than only point estimates.

## Threats and limitations

- The released outputs are historical samples; LLM nondeterminism is not re-estimated.
- Five LPR runs share the same benchmark suite and may not characterize model/API drift.
- The headline percentage depends on the aggregation convention; both mean-of-case ratios and ratio-of-totals are recorded.
- Historical compiler binaries, model versions, and serving stack may be difficult to recreate exactly.
- Benchmark examples predate current frontier models and may now be present in training corpora, creating leakage risk for modern reruns.

## Most valuable extension: model-drift × budget-normalized LPR

Re-run the same reduction protocol on **post-training-cutoff compiler bugs** with several current and historical models while fixing the oracle-call, wall-clock, and token/API-cost budget. Compare:

1. Vulcan only;
2. original LPR prompt/control loop;
3. LPR with current small/open model;
4. LPR with current strong model;
5. LPR with transformations mined from a held-out corpus but no runtime LLM.

Report final token count, oracle calls, accepted/rejected transformations, wall time, model cost, failure category, and variance across repeated runs. This separates the contribution of the LPR control architecture from model capability, benchmark leakage, and model/service drift.
